1. Scope and reading guide

The specification covers the peer-to-peer API of the package (routes group sync-api, src/Config/Routes.php), its signing scheme (src/Libraries/Signer.php, src/Filters/SyncHmac.php), the client (src/Libraries/SyncClient.php), the identifiers and fingerprints stored or exchanged (src/Libraries/Support.php, src/Libraries/FileSync.php) and the Telegram webhook. It does not cover the application tables that are synchronised, the conflict admin UI (Shield session, not part of the peer protocol), or the installer.

Status. A self-review written from the source, not an independent security audit. The test suite exercises the library through in-process transports; it does not run a real HTTPS round trip between a SyncClient and a SyncController.

2. System model

  • Nodes. Each node has a name (sync.node) and a database. A node knows its peers by name (sync.peers, or the single peerNode/peerUrl pair).
  • Roles. A dial-in node has a URL that peers connect to. A passive node (passive = true, behind NAT) is never connected to: it pulls from and pushes to its hub. A relay hub (relay = true) re-journals what it applies so its other peers receive it, tagging the entry with origin.
  • Data. Rows of configured tables are tracked in a journal (sync_changes) and a registry (sync_row_meta: uuid, rev, peer_rev, row_hash, base_blob). Files under sync.files.dir are tracked in sync_files.
  • Direction. Every request is an HTTP POST from a node to a peer's URL. The server side is stateless apart from the nonce cache and the database. There is no server-initiated message.
  • Trust. All nodes of a deployment share one secret, sync.secret. Possession of that secret is the only credential of the protocol (see 5 and 8).

3. Transport and message envelope

3.1 Request

ElementDefinition
MethodPOST only. Any other method is answered 405 method.
URL<peerUrl>/<routePrefix>/<endpoint>, default prefix sync-api. The client refuses any scheme but https (localhost excepted) unless sync.allowInsecure is set.
Bodyapplication/x-www-form-urlencoded, produced by http_build_query($params, '', '&') (RFC 1738 encoding, space as +). Structured values (lists of changes, row state) are PHP serialize() strings placed inside one form field.
X-Sync-NodeSender's node name: non-empty, at most 64 characters, no LF. Covered by the signature, see 3.2.
X-Sync-TimestampInteger Unix seconds at the sender.
X-Sync-NonceClient: 16 random bytes, lower-case hex (32 chars). Server accepts any non-empty string of at most 64 characters.
X-Sync-SignatureLower-case hex HMAC-SHA256, see 3.2.

3.2 Request signature

body_hash = hex( SHA-256( raw_body ) )
message   = "POST" LF path LF node LF timestamp LF nonce LF body_hash   (LF = 0x0A, no trailing LF)
signature = hex( HMAC-SHA256( key = sync.secret as raw bytes of the string, message ) )

path is '/' . routePrefix . '/' . endpoint on the client and '/' . trim(uri_string(), '/') on the server; the query string, the host and the scheme are not part of it. node is the value of X-Sync-Node, so the sender identity is authenticated by the same MAC as the rest of the request. The method is upper-cased by Signer::sign; the filter passes the constant "POST". sync.secret is used as the ASCII string it is configured as (the installer writes 64 hexadecimal characters, which are used as 64 bytes of text, not decoded to 32 bytes).

3.3 Response

ElementDefinition
Status200 on success. Rejections are 400, 401, 403, 405 with a short plain-text body and no signature.
Bodyapplication/octet-stream, the PHP serialize() of an associative array that always contains time (float, the server's microtime(true)). JSON is not used on the peer API.
X-Sync-Signature (200 only)hex( HMAC-SHA256( sync.secret, "response" LF request_nonce LF hex(SHA-256(response_body)) ) ). It binds the answer to the request nonce, not to the path, status or sender.

The client rejects any non-200 status, compares the response signature with hash_equals, and then calls Support::unpack, which is unserialize($blob, ['allowed_classes' => false]): no object is instantiated, and a payload that is not an array is an error.

4.3 Telegram webhook (not HMAC)

POST <routePrefix>/telegram, JSON from Telegram. Authenticated by the header X-Telegram-Bot-Api-Secret-Token compared with hash_equals to sync.telegram.webhook_secret (an empty configured secret rejects everything), and by callback_query.message.chat.id equal to sync.telegram.chat_id. The decision is carried in callback_data, matched against ^r:([A-Za-z0-9_.-]+):(\d+):([lr])$ = r:<node>:<conflict id>:<l|r>. The user that pressed the button is recorded as telegram:<username|id>; if sync.telegram.allowed_users is set, other users are refused.

5. Keys and derived values

6. Receiver processing rules

Order in SyncHmac::before; the first failing step ends the request.

  1. Method is POST, else 405. Body longer than maxBody (default 8 MiB) → 413.
  2. Signer::verify: secret not empty; |now − timestamp| ≤ replayWindow (default 300 s); nonce non-empty and at most 64 characters; node non-empty, at most 64 characters, no LF; hash_equals(expected, signature). Failure is logged with the caller's IP and answered 401 unauthorized without telling which check failed.
  3. X-Sync-Node must be a configured peer name, else 403 unknown node. The name becomes the sender of the request.
  4. Nonce claim (NonceStore): already present → 401 replay; otherwise stored. Claimed atomically (INSERT IGNORE on the primary key of sync_nonce); without that table the cache is used if it verifiably stores values. No usable store → 503.
  5. The signed request timestamp is recorded as a coarse clock sample of the sender (sync_cursor.clock_*); the client records a precise one from the time of each answer.
  6. The controller runs. On 200 the filter appends the response signature.

Row application: unknown table → skipped; origin equal to the local node → echo, ignored; otherwise the Reconciler decides fast-forward, three-way merge, last-writer-wins or quarantine. A change whose parent row is missing stops the batch (stopped), and the cursor advances only over entries that were handled.

File path confinement (FileSync::resolve): empty path, a NUL byte, a leading /, a drive prefix (X:) and any .. or empty segment are refused. Names that match the ignore patterns or contain .conflict- are refused on put and get; get also refuses links on the path and real paths outside the base.

Incoming rows are reduced to the columns the local table has and never set the primary key.

8. Threat model

8.1 Assets

  • Integrity of the synchronised rows and files on every node (a forged change is applied as if a peer wrote it).
  • Confidentiality of row contents and files in transit and in the journal tables (payload, base_blob hold full rows, including those of sensitive tables such as users).
  • sync.secret and sync.telegram.* in .env.
  • Availability of sync and of the edit lock (auth-lock) that blocks writes on a node.

8.2 Adversaries and assumptions

AdversaryCapability assumedHandled by
A1 — Network observer / active attacker without the secretReads, drops, delays, replays or modifies traffic.HMAC over method, path, time, nonce, body; time window; nonce cache; signed responses. Confidentiality relies on TLS; the client refuses plain http:// peers, the server cannot see how a request arrived.
A2 — Internet scannerSends arbitrary requests to /sync-api/*.All peer routes need a valid signature; failures are uniform 401 and logged with the IP.
A3 — Holder of the secret (a compromised node or a leaked .env)Can build any valid request.Not mitigated. One shared secret: it can act as any peer, write any configured table, read any bootstrap table and any file under the files directory.
A4 — Malicious or buggy authenticated peerSends well-signed but wrong data.Table allow-list (opt->table), allowed_classes=false, revision/hash comparison, quarantine of conflicts, path confinement for files, 4 MiB file limit, maxBody and maxPushChanges. Semantic validity of row values is the application's concern.
A5 — Other member of the Telegram chatPresses decision buttons.Webhook secret and chat id; optionally sync.telegram.allowed_users.
A6 — Local user of the web hostReads .env, writable/.Out of scope; file permissions are a deployment matter.

Assumptions: peer URLs use HTTPS with certificate verification (the client sets verify = true); clocks of the nodes differ by less than replayWindow; the database is shared by all PHP workers of a node (for the nonce check); the secret is generated with a CSPRNG and kept private.

8.3 Properties the signing scheme provides

  • A request cannot be altered in body, path, timestamp or nonce without invalidating the signature (SHA-256 of the body is inside the MAC; comparison uses hash_equals).
  • A captured request cannot be replayed after replayWindow seconds, and not at all while its nonce is stored.
  • A response cannot be accepted for a different request nonce or with a different body.
  • Unserialising peer data cannot instantiate classes.
  • The server never connects to a URL supplied in a request (probe uses the configured URL).

10. What the repository does not guarantee

10.1 Security

  • No confidentiality at the application layer. Bodies are signed, not encrypted. Protection in transit depends on HTTPS; the client refuses plain HTTP peers, the server cannot enforce it.
  • No per-node identity or non-repudiation. A shared MAC key cannot show which node produced a message; any node can produce messages in the name of another.
  • No protection once the secret leaks. No forward secrecy, no revocation, no rotation protocol, no detection of its use from another place.
  • No end-to-end authenticity of a row across a relay: the hub re-journals what it applied under its own revision; a compromised hub can alter or fabricate rows for its other peers.
  • No protection of data at rest. The journal and registry tables keep full row images (including users and password hashes if those tables are synchronised); backups of them carry the same data.
  • No rate limiting, lockout or abuse detection on the peer API beyond logging a warning on a bad signature and the size limits.
  • The credentials of mail (SMTP) and Telegram are stored in clear in .env; alert mail is sent as the configured SMTP transport allows and is not end-to-end encrypted.

10.2 Correctness and availability

  • Convergence is conditional. Version counters are exact for two parties and approximate for three or more; the docs require writers declarations for tables that travel through a relay between three or more nodes.
  • Last-writer-wins depends on clocks. changed_at is the sender's wall clock. Differences below clockTolerance (2 s) are decided by the tiebreak order and a peer whose measured offset exceeds clockMax (5 s) is not trusted (quarantine, tiebreak for files); between the two, skew can still make an older edit win. The offset is measured per node with its own error, so close to clockMax the two nodes may decide differently; the escalated conflict then needs a human.
  • Delivery is at-least-once and idempotent, not exactly-once. Ordering is per sender journal; there is no global order and no cross-table transaction across nodes. A child whose parent has not arrived stops the batch.
  • Retention. sync:prune deletes only journal entries that the peer reports as applied, and nothing if the peer cannot be asked; a peer that stays offline longer than the retention must be re-bootstrapped (docs/OPERATIONS.md).
  • Conflicts may be quarantined and need a human decision; until then the two nodes differ.
  • The edit lock is a lease, not a distributed mutual exclusion proof; it ends when the lease expires or the holder is unreachable (reason says so).
  • File sync compares by SHA-256 and mtime; two edits are resolved by newer mtime and the loser is kept as .conflict-<node>-<ts>. Pushes are limited to 4 MiB, symlinks are not synchronised, directories are removed only when empty, and the hub is only as available as its schedule (a pull every 5 minutes in the reference deployment).
  • Not a backup. A destructive change is replicated like any other.
  • Telegram and mail are best effort. A failed delivery is logged; the sync does not depend on it.

10.3 Verification

  • The automated tests use in-process transports and SQLite3 fixtures (tests/TwoNodes.php); they do not cover a real HTTPS exchange, the Telegram and SMTP services, a hostile peer, or load. The 413/503 filter paths and allowed_users have no test beyond option parsing.
  • This document has no third-party sign-off.
  • The version, behaviour and configuration of the host application, the web server, PHP and the TLS terminator are outside the repository.

11. Reproducing the vectors

<?php
require 'vendor/autoload.php';
use AdGo\Sync\Libraries\{Signer, Support};

$secret = str_repeat('ab', 32);
$ts     = 1790000000;
$nonce  = '00112233445566778899aabbccddeeff';
$path   = '/sync-api/pull';
$body   = http_build_query(['after' => 41, 'limit' => 2], '', '&');

$node   = 'site1';

echo Signer::sign($secret, 'POST', $path, $node, $ts, $nonce, $body), "\n";
echo Support::seedUuid('items', 7), "\n";
echo Support::hashRow(['id' => 7, 'name' => 'Widget', 'qty' => 5]), "\n";
echo sha1('labels/2026/a.pdf'), "\n";
$sig = Signer::sign($secret, 'POST', $path, $node, $ts, $nonce, $body);
echo json_encode(Signer::verify($secret, 'POST', $path, $node, $ts, $nonce, $body, $sig, 300, $ts + 301)), "\n";

Run from the package root (PHP 8.4). Expected first line: b0ba0538f33337756979493da98f5f10d96b365bc74a2853131f2c4c167addc9; the last line prints the timestamp outside the replay window rejection.
